1. Introduction

AI Multilingual is a multilingual layer for WordPress. It keeps one canonical source object per content item and applies language overlays at render time — titles, body segments, taxonomy labels, selected WooCommerce surfaces, and SEO metadata where Supported.

Version 1.6.0 focuses on administrator completion: Localized URL operator surfaces, Jobs / stale / conflict literacy, and documented Rank Math Model A SEO expectations. Schema target remains 8 with no database migration.

What can I do with this plugin?

  • Configure a default (source) language and additional target languages.
  • Translate posts, pages, products, and admitted taxonomies via Multilingual → Workspace.
  • Run background translation Jobs (including multi-post “Bulk translate”) without hand-typing segment keys.
  • Understand stale and conflict outcomes without silent overwrites.
  • Review and publish translation segments under the publication gate model.
  • Prepare and publish Localized URL slugs for Supported shapes (posts/pages/products and admitted terms).
  • Coexist with Rank Math for SEO overlays and sitemap language relationships (Model A).
  • Optional Enable Gutenberg block translation via Strategy F Settings flags (defaults Off). Elementor support exists in product contracts but has no Settings toggles in v1.6.0 — see Elementor.

Operating model Source content stays authoritative in WordPress. Translations are overlays. Visitors see overlays when eligibility rules pass (language state, publication gate, route/overlay rules). Preview languages remain source-slug for Localized URLs.

2. Quick start

Goal: from a fresh install to your first successful translation on the front end. Details live in later sections — follow this path first.

Recommended first 15 minutes

  1. Install and activate the plugin (or confirm AI Multilingual is active).
  2. Open Multilingual → Languages. Confirm the default language. Add at least one target language (state Published or Preview). Details: Initial configuration.
  3. Open Multilingual → Settings. Leave Segment publication gate Off and auto-publication Manual until you understand review. Optionally enable the AI provider if you will use machine translation / Jobs.
  4. Open Multilingual → Workspace → Translate (or Operations). Select one page or post and a target language. See Translator Workspace.
  5. Create or run translation for key segments (manually or via Jobs → Create job → Translate missing, then Run now as an administrator). Review text; publish only if the gate is On (Review & publication).
  6. Visit the front end in that language and confirm overlays appear.
  7. Only after that first success, consider enabling Localized URLs in Settings and publishing a first route from Workspace (Localized URLs). Term archive slugs use the term edit screen panel (Taxonomies).
Caution Localized URLs default Off. Enabling starts background verification; while Activating, visitors may still see source-slug URLs.
Normal operator path Day-to-day work uses Workspace and Settings. REST/CLI are for diagnostics or advanced use only — see Advanced.

3. Initial configuration

Admin root menu title: Multilingual. Capability for Settings / Languages: WordPress manage_options.

Languages

Path: Multilingual → Languages.

  • Default language = source content. Always published and unprefixed. Cannot be treated like a normal target.
  • State: Preview (translators only), Published (everyone), Disabled (not routed; returns through Preview before Published again).

Adding a language

  1. In the Add a language card, choose a language from the searchable list (type an English or native name).
  2. If the language has more than one region, pick the Regional variant (for example Portuguese (Portugal) or Portuguese (Brazil)). Single-region languages skip this step.
  3. Check the read-only summary — URL prefix, Locale, Native name, Direction are derived for you and cannot be mistyped.
  4. Set Status and Sort order (pre-filled to the next value), then Add language.

The URL code and locale are fixed once a language exists — changing either would break every translated URL. To change them, delete the language and add it again. On Edit you can change status, sort order and the switcher display name; a custom language also lets you edit its name and text direction.

Advanced: custom language

The collapsed Advanced: add a custom language section is for locales outside the standard list — you provide every value by hand. It can be turned off site-wide with the aiml_allow_custom_language filter.

The standard language list is bundled with the plugin (derived offline from WordPress/GlotPress locale data). It needs no internet connection and no installed language packs.

Languages are stored separately from the Settings option. Two languages can never share a locale. Changing languages later is supported; disable carefully if URLs/SEO already rely on a language.

3a. Regional preferences

Supported Signed-in users can store a preferred language. That value is a preference, not the current page language. The URL (and Localized URL routing when On) remains the language visitors actually see.

  • WordPress profile: Users → Profile → Regional Preferences → Language.
  • WooCommerce: My Account → Account details shows the same language field when WooCommerce is active.
  • Default: when a user has not chosen a language, the site uses WordPress WPLANG (empty site locale is treated as en_US).
  • Saving: choosing a published/preview language stores that code. Clearing the field restores the site default.
Preferred vs current Preferred language does not rewrite the current URL or anonymous cache. Visitors still see the language of the URL they opened. Universal Multicurrency may show a matching currency field in the same Regional Preferences section when that plugin is active — it is optional composition, not a required dependency.

3b. Floating language selector

Optional An edge-docked language control on the public site. Default Off. Leave it Off unless you want a visitor-facing switcher in addition to any theme/menu switcher.

  • Enable: Settings → Enable floating selector. Until then the control is absent from the front end.
  • Side / vertical: left or right edge; top, center, or bottom.
  • Collapsed look: language code, language name, or globe icon. No country flags.
  • Preset: Edge pill, Minimal, or Tab.
  • Desktop / mobile: two checkboxes hide the same markup with CSS. There is no separate mobile HTML or device sniffing.
  • Without JavaScript: each language is a normal link. Users can still change language.
  • Keyboard: the collapsed control is a disclosure, not a listbox. Focus and Escape behave as a disclosure.
  • Signed-in persist: when “Remember language for signed-in users” is On (default), a click best-effort saves preferred language. Navigation never waits on that save. Guests get no language cookie.

The selector uses the same switcher URLs as the rest of the plugin. It does not change routing, cache keys, or anonymous language authority.

4. Translator Workspace

Path: Multilingual → Workspace (page title Translator workspace).

Views (tabs): Operations · Translate · Review queue · Jobs.

Related admin screens (same top-level menu): Languages, Settings, classic Translate (capability aiml_translate), Glossary, Limited Rollout, and SEO Diagnostics. Day-to-day operator work for v1.6.0 centers on Workspace and Settings.

  • Operations — find content needing attention (stale, conflicts, publication), open detail, edit/review, inspect Localized URL slug panel for posts/pages/products.
  • Translate — work segments for a selected source + language.
  • Review queue — items awaiting review (requires review capability).
  • Jobs — create, monitor, and recover background jobs.

Workspace language pickers exclude the default language and disabled languages.

Typical actions on a segment/detail: edit translated text, submit/review where available, publish/unpublish under gate rules, retranslate when admitted, open Localized URL slug tools.

5. Translating content

Translate with AI (one page)

On the Translator Workspace editor, once a page and a target language are loaded, click Translate with AI. Pick a mode:

  • Translate missing (default) — only segments with no translation yet.
  • Retranslate stale — machine translations whose source text changed.
  • Retranslate AI translations — every existing machine translation, stale or not (a confirmation explains what is replaced).

The action runs a background job, starts it immediately, and refreshes the editor when it finishes with a plain summary (N translated · M kept · F failed). You can close the browser while it runs. Manually edited, reviewed and in-review translations are never replaced by any mode — they are counted as “kept”. If AI translation is not configured, the button stays visible but disabled with a link to the settings screen (administrators only).

The older Multilingual → Translate screen now links straight into this flow with the page and language preselected.

Working with many languages at once (one page)

On the Workspace editor, the Languages to work on checklist (all target languages checked by default) picks which languages the page is loaded for. After Load, a tab strip shows one tab per selected language with its state badge, and a “N / M languages ready” bar. M is every configured target language — a language you never selected still counts, so a forgotten language is always visible; N is the languages that are complete and clean (nothing missing or stale, no quality errors, and reviewed/translated). Clicking a tab switches the active language without reloading the page — Translate with AI and the review actions act on the active tab. A page-actions menu adds Translate all selected languages with AI and Approve all ready languages.

Translate with AI (many pages × many languages)

Workspace → Site Translate, or select pages/posts in the WordPress list table and choose the Translate with AI bulk action. Tick the objects and the target languages (all checked by default), then Translate selected with AI. A pre-run line shows the count as “5 pages × 3 languages = 15 translations” — this is the number of page-and-language operations, not a token or cost estimate. The jobs are created and started in one step (one background batch); progress, failures and retry are on the Jobs view. Retrying a batch only creates the page-and-language pairs that are still missing.

Translating into an already-published language

Universal Multilingual never changes a language's publication status and never publishes content for you. But a translation written into a language that is already published may become visible to visitors immediately under the site's existing rendering policy. So whenever a bulk or multi-language run targets one or more published languages, you must tick an acknowledgement (“I understand and want to continue”) before it will start — the server rejects the run otherwise. Preview-status languages render for signed-in editors only and need no acknowledgement.

Posts & pages

Use Workspace Operations/Translate. Hierarchical pages share the Localized URL panel with posts once Localized URLs are On and shapes are admitted.

WooCommerce products

Optional dependency Product titles/descriptions and Supported catalog surfaces overlay when translated. Localized product URLs use the Workspace slug panel (including admitted %product_cat% permalink setups). See WooCommerce.

Categories, tags, taxonomies

Term names/descriptions translate where Supported. Localized archive slugs for admitted taxonomies use the term edit screen panel (not CLI). Unsupported taxonomies simply omit the panel.

Gutenberg

Requires Strategy F flags enabled in Settings (defaults Off). Only listed core blocks are Supported. See Gutenberg.

Elementor

Supported widget families exist in product contracts; flags default Off and are not exposed in Settings UI in v1.6.0. See Elementor.

6. Jobs

A Job is a background batch that translates (or retranslates) segments for one or more posts using Action Scheduler. Ordinary create/monitor/recover is Workspace → Jobs.

When to use Jobs

  • Translate many missing segments on one post.
  • Retranslate stale machine-translated content after source changes.
  • Bulk-translate multiple posts without listing segment keys.

Creating a Job

  1. Open Jobs → Create job.
  2. Choose Job type:
    • Translate selected — explicit segment keys; may overwrite machine-translated when allowed.
    • Translate missing — fills missing segments (default in UI).
    • Retranslate stale — targets stale segments; may overwrite machine-translated when allowed.
    • Bulk translate — post IDs only; missing segments resolved automatically (no segment keys).
  3. Enter post IDs (one per line) and optional segment keys / idempotency token as required.
  4. Click Create job. Creating does not auto-start processing.

Bulk help (UI): up to 50 posts per bulk request; each job may materialize up to 500 items; after create, use Run now (administrators).

Running & monitoring

  • Expand the job row. Administrators with run capability see Run now when Waiting.
  • Editors without run capability see that an administrator must run the job.
  • Progress example: N done · N failed · N skipped/stale · N total.
  • Other actions (capability-gated): Pause, Resume, Cancel, Retry failed.

Outcomes (operator labels)

Navigation: Open source in Operations deep-links by source type/id/language (source-level; not translation-id enriched).

Safety Jobs never silently overwrite protected targets. Conflict protection is intentional.

7. Stale translations

Stale means the source changed after the translation was produced (Store is_stale). It is not the same as a Job item labeled “Source moved during job”.

Why it happens

Editing source content marks related translation segments stale so operators know review/retranslate may be needed.

Published vs unpublished

  • Stale — still published — remains published until you edit or retranslate. Visitor display still depends on overlay and route eligibility.
  • Stale — not published — currently unpublished; edit/retranslate before expecting public overlay; gate settings may still apply.
Do not assume universal source fallback Frontend behavior is path-dependent. Classic overlays may still show the existing translated text while stale; Gutenberg block lookup rejects stale segments; Extension visitor resolution may miss stale segments. Always verify the surface you care about.

What to do

  1. Open Operations for the source + language.
  2. Review differences; edit manually or create a Retranslate stale Job when admitted.
  3. Publish again if your gate requires it.

8. Conflicts and safe recovery

AIML prevents silent overwrites when a target is protected (for example reviewed/manual edits conflicting with a Job).

  • Job item: Skipped — conflict protected (internal status skipped_conflict).
  • Hint: open Operations or Translate to review/edit, or use confirmed Retranslate when allowed — Jobs will not silently overwrite.
Intentional protection Do not try to bypass conflict safeguards. Resolve by human review, then retranslate or retry only through admitted actions.

9. Review and publication

  • New machine translations typically start unpublished when using the publication model introduced in TI.7 (gate defaults Off for safe upgrades).
  • With Segment publication gate Off, public overlay eligibility follows pre-gate rules (non-empty, not ignored/missing).
  • With gate On, segments must be published to be publicly overlay-eligible. Enabling the gate does not mass-unpublish existing content.
  • Auto-publication mode (Manual / Approved only / Controlled auto) affects future automatic publish after machine translate — not a mass rewrite of history.
  • Review queue uses review statuses such as not submitted / pending / approved / rejected (Workspace types).

If a translation exists but is not publicly eligible, visitors continue to see source (or prior eligible overlay) according to surface rules — treat “exists in Workspace” ≠ “visible on front end” when the gate is On.

Review queue — one card per page, all languages

The Review queue is grouped by content object: one card per page/product showing every target language together, with a per-language tab strip and the same “N / M languages ready” bar as the Workspace. A language that is not translated, incomplete, needs attention, pending, ready or complete is always shown on the card, so a single-language view can never hide a forgotten language. The card paginates by object — one page's languages are never split across pages.

Approve all ready languages approves every currently pending segment for every language on the card that is clean (nothing missing, stale, rejected, or quality-blocked), processing the whole pending set — not just the first batch — for each language. A language that needs attention is listed as skipped, never silently approved, and the result says plainly when the object is not fully reviewed. Per-field and per-language approval still work exactly as before.

10. Localized URLs

Supported Optional localized path slugs for admitted shapes. v1.6.0 does not add new routing capability — it exposes the Supported lifecycle to administrators (P0).

Why use them

Give target-language URLs human-readable slugs (for example a Swedish product path) while Rank Math / SEO Model A continue to own primary sitemap locs as documented below.

Enable / disable

  1. Multilingual → Settings → Localized URLs.
  2. Enable localized URLs (or Retry activation if Failed).
  3. Wait until State is On. While Activating, visitors may still see source-slug URLs.
  4. Review Capability admission and Hierarchy reindex / frontier on the same screen.
  5. Disable localized URLs takes effect immediately when used.

Posts, pages, products (Workspace)

  1. Open Workspace, select content + language.
  2. Panel Localized URL slug:
    • Generate candidate from translated title, or type and Save candidate.
    • Review Origin, Effective path, Sync.
    • Publish route when ready.
    • Clear / Refresh as needed.

Terms / archives

On term edit screens (for example Posts → Categories), use the Localized URLs panel: Generate / Save candidate / Clear / Publish route / Refresh. Same collision recovery as posts.

10a. Localized URL collisions

If a path is already taken (another route or reserved/history path), publication is blocked and the UI reports a collision.

Recovery: edit the candidate, Clear, or try a different slug, then Publish route again. Help text: “That path collides with another route. Edit the candidate, clear it, or try a different slug, then publish again.”

Generated candidates may be adjusted; manual candidates that collide stay blocked until you change them. Degraded frontier children often mean rematerialization hit collisions — not that the shape is unsupported.

11. SEO / Rank Math

Supported AIML overlays translated SEO metadata (titles/descriptions where integrated), emits hreflang / x-default relationships, and aligns canonical / Open Graph URL identity with EffectiveUrl on Supported Localized URL requests.

Sitemap Model A (Rank Math)

  • Rank Math owns primary sitemap <loc> entries (default/source language).
  • AIML does not create duplicate localized primary <url> entries.
  • AIML may enrich qualifying Rank Math entries with xhtml language relationships when discoverability gates pass (site public, enough public languages, SEO set eligibility).
  • Non-public sites (blog_public = 0, “Discourage search engines”) may correctly omit xhtml advertisement — this is EXPECTED OMIT for that configuration, not a claim that xhtml alternates are generally absent on public sites.
  • v1.6.0 characterization: no Supported-contract defect; no sitemap architecture redesign.

Admin tool: Multilingual → SEO Diagnostics (manage_options).

13. Gutenberg

Enable Strategy F flags under Settings (all default Off). Enable prerequisites in order; check Strategy F diagnostics on the Settings page (Combination valid, Frontend rendering active).

Supported blocks (examples): paragraph, heading, button, list-item, preformatted, verse, code, quote, details, pullquote, image, file, audio, video — plus structural hosts that carry children (group/columns/list, etc.).

Deferred Navigation, Query Loop, reusable/synced patterns, FSE templates, table, search, custom blocks, ambiguous Woo blocks.

Unsupported core/html, core/shortcode, core/embed.

Stale Gutenberg segments are rejected by block lookup (they do not overlay) — verify after source edits.

19a. Site Translate (pages, posts, products)

Supported Multi-object translation workflow in Workspace → Site Translate for admitted visitor-facing types: pages, posts, and products.

Prerequisites

  • Target language configured (Preview while preparing; promote to Published before anonymous/public acceptance).
  • AI provider configured; segment publication gate On; auto publication Manual (AI output lands unpublished until you Publish).
  • Gutenberg block bodies: Strategy F must be fully valid when the selection includes block-dependent objects. Classic-only selections may run even when Strategy F is Off.

Coverage meanings

Coverage is per object × language from current extraction ∩ provider-admitted segments (slug candidates excluded). No extractable work means eligible_total=0 — not “100% translated.” Translation completeness for publish intent requires missing=0 and stale=0; unpublished translated segments may remain.

Jobs batching

Selections chunk at 50 objects per Job; one Site Translate operation shares one batch_id. After create, Workspace focuses the Jobs tab on that batch. Run batch now enqueues waiting jobs asynchronously (does not run the whole site synchronously in one request).

Localized URLs sequencing

  1. Finish translation Jobs; segments remain unpublished until you Publish.
  2. Promote language Published; keep Localized URLs Off; verify anonymous gate holdback on language-prefixed source slugs.
  3. Publish segments in Operations.
  4. Enable Localized URLs; use Generate & publish routes for the selection.

Automatic slug generation requires a published, non-stale translated title. Outcomes include title_not_published, title_stale, and collision (edit / clear / retry per item — no automatic slug-2 suffixes).

19. Recommended operating workflow

Reflects v1.11.0 operator surfaces including Site Translate, Localized URL completion, Rank Math Model A documentation, and Jobs / stale literacy.

  1. Edit source content in WordPress/WooCommerce.
  2. In Workspace → Operations, inspect stale / attention for each target language (Stale).
  3. Create a Job from Workspace → Jobs (Translate missing, Retranslate stale, or Bulk translate). Creating does not start work — an administrator uses Run now (Jobs).
  4. If the job ends Completed with skips, expand Details. Resolve Skipped — conflict protected in Operations (Conflicts); for Source moved during job, create a fresh job after the source is stable.
  5. Review translations in Workspace; publish under your gate policy (Review & publication).
  6. If Localized URLs are On: for posts/pages/products use the Workspace Localized URL slug panel (Generate / Save candidate → Publish route → check Effective path / Sync). For admitted terms, use the term edit screen Localized URLs panel the same way (Localized URLs, Taxonomies). Recover collisions with Edit / Clear / retry (Collisions).
  7. Verify the front end (and Rank Math SEO expectations if used — SEO / Rank Math).

Daily / weekly checklist

  • Jobs: any Waiting needing Run now? Failed / Completed with skips?
  • Operations: stale published segments reviewed?
  • Settings: Localized URLs state On? Capability admission honest? Frontier Complete (not Failed / Degraded without review)?
  • Provider key/model still valid?
  • New products/pages/terms: translations + Localized URL routes for priority languages?

20. Current limitations (v1.12.0)

  • Floating language selector is opt-in (default Off); it does not replace theme/menu switchers.
  • Preferred language is a signed-in preference only — it does not change the current URL language or set an anonymous cookie.
  • Site Translate covers pages/posts/products only (not menus/terms one-click).
  • Jobs → Operations linking is source-level only (no translation_id enrichment).
  • Richer multi-language UX polish remains backlog.
  • Sitemap xhtml advertisement remains subject to public/discoverability eligibility (including blog_public).
  • Translated rewrite bases, Woo endpoint names, pretty layered-nav: Deferred.
  • Distinct variation Localized URLs: Unsupported.
  • Gutenberg/Elementor flags default Off; Elementor has no Settings toggles in v1.6.0.
  • Provider-generated slugs, rewrite-rule ownership, competing sitemaps, fuzzy URL matching: Unsupported.
  • No silent conflict overwrite; Run remains administrator-gated.

Administrators normally do not need these. Developers:
