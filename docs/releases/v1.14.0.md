# Universal Multilingual — Release Notes v1.14.0

**Status:** prepared (not tagged / not released)
**Release version:** 1.14.0
**Schema target:** **10** (`step_10_promotion_foundation`: `aiml_object_identity`,
`aiml_promotion_state`, `aiml_promotion_log`)
**Settings schema:** **3** (`promotion_max_package_bytes`, `promotion_log_retention`)
**Package:** `universal-multilingual-1.14.0.zip`
**Previous release tag:** `v1.13.0`
**ADR:** `docs/adr/0030-devprod-translation-promotion.md` (Accepted)

This minor release adds a first-class **DEV → PROD translation promotion**
module: move reviewed translations between independent WordPress installs
safely, without copying database tables or trusting numeric ID parity. Nothing
in the existing translation, routing or rollout behaviour changes; the module is
disabled in the sense that it does nothing until an operator runs an export or
import.

## Highlights

### Export → dry-run → apply

1. On the source site, **Universal Multilingual → Translation Promotion →
   Export**: pick target language(s) and optional scope (post type, id list,
   "approved only", "published only", "changed since"). Downloads one `.json`
   package.
2. On the target site, upload the package. **Validate & dry-run** is strictly
   read-only: schema + dual-checksum validation, per-object resolution,
   per-language resolution, and a category for every incoming segment. It writes
   nothing and fires no action hooks.
3. Review the summary (new / update / unchanged / conflict / stale source /
   missing / route conflict / …), choose an apply mode, and **Apply**. The
   browser re-sends the package; the server verifies a stateless signed review
   token and re-plans — any drift since the reviewed dry-run refuses the whole
   apply.

### Cross-environment identity

`aiml_object_identity` holds a plugin-owned UUID and a deterministic,
environment-independent natural key (`post|type=…|ancestors=…|slug=…` /
`term|taxonomy=…|ancestors=…|slug=…`, stored as `TEXT`, indexed through its
sha256). Export mints the UUID **before** serialization. The target site
bootstraps by natural key on the first promotion and adopts that UUID; every
promotion afterwards is UUID-joined and survives a rename on either side. A
mapped source that no longer exists, or a local object already joined to a
different lineage, is `identity_conflict` and is never force-applied.

### Three-way merge

`aiml_promotion_state` records, per promoted `(object_uuid, language, segment)`,
the translation and source hash last written by a promotion. An import compares
the current local translation hash against that baseline to tell an ordinary
`update` from a `conflict_target_modified` (edited independently on the target).
`stale_source` and both `conflict_*` categories are never applied in Safe mode.

### Apply modes

- **safe_only** (default): `new` + `update` only.
- **selective**: an explicit per-row allowlist; `stale_source`,
  `conflict_target_modified` and `route_conflict` additionally need a per-row
  acknowledgement.
- **force**: applicable conflicts + stale rows — still never `identity_conflict`
  / `ambiguous_source`.

Writes go through `Store::save_translation()` / `save_slug_candidate()` with the
target's own current source text, so `source_hash` / `is_stale` stay consistent.
Route rows (`aiml_slug_routes` / `aiml_route_history`) are a per-environment
projection and are never exported — only the translated slug candidate is
imported, and the target's own routing services rebuild the routes.

### Scope (milestone 1)

`post`, `page`, `product` (title / slug / excerpt / content — content-body only
where both sides have block-identity parity), Rank Math SEO meta, and
`product_cat` / `product_tag` term name + description. `nav_menu_item`, `pa_*`
attributes, product variations, Elementor, FluentForms and hosted-key term
translations are reported `unsupported_type` and added in a later milestone.

### Capabilities

`aiml_promote_translations` and `aiml_trust_promoted_review_state`, both
**`administrator` only** by default, provisioned through a versioned
`aiml_caps_version` option on activation and on `admin_init` (bind-mount safe).
Sites widen the promoter set with the `aiml_promotion_can_promote`
`map_meta_cap` filter. The trust capability is required to carry an
approved/published review state across environments — done through the existing
review / publication services, never by writing columns.

### Surfaces

- REST: `POST aiml/v1/promotion/export`,
  `POST aiml/v1/promotion/import/validate`, `POST aiml/v1/promotion/import/apply`,
  `GET aiml/v1/promotion/history`.
- Admin: a vanilla (`wp-api-fetch`) screen under Universal Multilingual.
- CLI: `wp aiml promotion export | import [--dry-run|--apply --mode=] | history |
  backfill-identity`.
- `do_action( 'aiml_promotion_audit', $event )` — `export` / `apply_start` /
  `apply_row` / `apply_complete` stages only (no dry-run stage). History in
  `aiml_promotion_log` (bounded, last ~200 rows).

## Benchmarked limits (WP1)

- Hard package ceiling: **25 MB** decoded.
- Soft warning: ~12 MB.
- Object cap: **3,000 objects** per package.

Exceeding the object cap fails the export with a "split by language / scope"
message. `plan()` and `apply()` run in a single synchronous request — no Action
Scheduler.

## Upgrade / compatibility

- Additive schema step 10; no `aiml_translations` column; existing translation
  data untouched. Fresh install and upgrade-from-9 (with or without the
  activation hook) both land at schema 10 and grant the two capabilities.
- Package `format_version == 1` only. A newer package is rejected cleanly.

## Deferred

- Real-provider / browser-AT QA of the admin screen against a genuine two-site
  setup (a Playwright suite runs one WP install with two content sets).
- Operator "manual map" UI for the low-confidence fingerprint / rename-before-
  first-promotion case.
- Hosted-key term promotion (ADR-0021).
- Media / attachment ID remapping (imported verbatim; advisory dry-run note).
