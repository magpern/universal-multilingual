# Universal Multilingual — Release Notes v1.20.0

**Status:** released
**Release version:** 1.20.0
**Schema target:** **10** (unchanged — no migration)
**Settings schema:** **3** (unchanged)
**Package:** `universal-multilingual-1.20.0.zip`
**Previous release tag:** `v1.19.0`

Minor release. Approving a page's translation now also publishes its
localized URL. No schema change.

## Why

Approving a page/language's content and publishing its translated URL were
two separate, manual actions: "Approve page" (or "Approve all ready
languages") in the Review Queue / Workspace, then a distinct "Publish URL"
click in the localized-URL panel. At the scale this is meant for — many
pages × many languages — that second click does not scale: an operator
running a bulk translate-then-approve pass has no practical way to also
remember a per-page, per-language "Publish URL" click for every one of them.

## What's new

### Approve → publish, one action

- `WorkspaceService::approve_object()` now attempts to publish the page's
  prepared localized-URL route for that language immediately after approving
  its pending content segments, using the existing `RoutePublicationService`
  (the same one the Workspace's "Publish URL" button calls) — no new
  publication logic, no relaxed collision/eligibility checks.
- `approve_object_languages()` ("Approve all ready languages") inherits this
  automatically, since it calls `approve_object()` per language.
- Best-effort and non-blocking: the attempt's outcome is reported in a new
  `route_publish: {attempted: bool, published: bool, reason: string}` field
  on the REST response. It never fails or rolls back the content approval —
  a page with no slug candidate yet, a language that isn't published, or a
  URL collision is simply reported as not published, exactly the reasons
  the manual "Publish URL" button already surfaces.
- The manual "Publish URL" button in the Workspace's localized-URL panel is
  unchanged and still needed for a page approved before this release, or for
  an approval that intentionally happened without a ready slug candidate.

## Upgrade notes

No database migration. No settings changes. No new REST endpoint — this
extends the existing `POST aiml/v1/workspace/<id>/review/approve-object` and
the "Approve all ready languages" action's response shape additively
(`route_publish` is a new field; no existing field changed).
